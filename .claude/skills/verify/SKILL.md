# Доказательство правки

Зелёная сюита здесь доказательством не считается. Причина измерена: при 36 зелёных тестах корпус дал 17 поражений против patch-package и 0 побед — тесты и разборщик писал один человек в одном представлении о формате.

Доказательства два: **корпус** (правка не изменила поведение на реальных патчах) и **мутация** (тест действительно закрепляет правку).

## Мутация — всегда

Каждая правка заканчивается этим. Снимаешь правку — тест обязан покраснеть; не покраснел, значит он проверяет не то.

```bash
SB=<каталог песочницы сессии>
cp src/файл.ts $SB/файл.bak          # копия ДО мутации
# ... внести мутацию (python3 с точечной заменой строки) ...
bun test -t "имя теста"              # ожидание: 0 pass, 1 fail
cp $SB/файл.bak src/файл.ts          # восстановление ИЗ КОПИИ
grep -n "<мутированная строка>" src/файл.ts   # убедиться, что вернулось
```

`bun test -t` фильтрует по **подстроке** имени, и под неё попадает не только твой
тест: на мутации «keeps the executable bit» нашлось два теста, и счётчик показал
`1 pass 1 fail`. Смотреть надо имя упавшего, а не счётчик:

```bash
bun test -t "имя теста" 2>&1 | grep -E "\(fail\)|^ [0-9]+ (pass|fail)"
```

**Никогда не восстанавливать через `git checkout <файл>`.** Работа в ветке обычно ещё не закоммичена, и `checkout` снесёт её целиком. Это уже случалось дважды.

Мутация, пережившая сюиту, — это дыра в тестах, а не повод пожать плечами. Исключение одно и описано в коде: проверка «патч не может быть записан за пределы `patches/`» в `writePatch` — до неё не добраться, `validateManifestField` отвергает такие поля раньше. Это второй замок на той же двери, оставлен намеренно.

### Мутация выжила — что это значит

Не всегда «строка лишняя». Проверенные случаи:

- **вторая проверка прячет первую.** `isSymbolicLink()` дублировал `!isFile()`; убрать дубль, а тест переписать так, чтобы он различал «пошли по ссылке» и «пропустили» (INS-9);
- **тест проходит случайно.** Тот же случай: исход зависел от порядка `readdirSync`. Признак — тест зелёный и с правкой, и без;
- **тест проверяет не то.** Многострочный аргумент передавался через `$(printf …)`, то есть подстановку шелла; на Windows приезжал литералом. Разбор аргументов звать напрямую, без шелла посередине (INS-10);
- **платформа скрывает дефект.** `create` не работал в изолированной раскладке нигде, кроме macOS: Apple diff разыменовывает симлинк-каталог, GNU — нет. С Apple diff мутация выживает всегда (INS-11).

### Прогон с GNU diff

macOS даёт Apple diff, CI на Linux и Windows — GNU. Правку, задевающую `create` или разбор вывода `diff`, гонять дважды:

```bash
bun test
PATH=/opt/homebrew/opt/diffutils/bin:$PATH bun test   # brew install diffutils
```

## Сравнение с прежним поведением — когда правка что-то сужает

Мутация проверяет, что тест держит **внесённую** защиту. Она ничего не говорит о
том, что правка отняла: тесты пишутся под новое поведение и старого не помнят.
Измерено на TSK-43 — два регресса подряд прошли зелёную сюиту и шесть проверок
CI, оба вида «раньше работало, теперь отвечает отказом» (INS-16).

Признак, по которому это надо проверять: правка **сужает условие поиска**,
добавляет чтение файла, которого раньше не читали, или меняет ключ, по которому
что-то находится.

```bash
SB=<каталог песочницы сессии>
git worktree add $SB/main main
# один и тот же сценарий двумя версиями CLI на одном дереве
bun $SB/main/index.ts <команда>          # как было
bun ./index.ts <команда>                 # как стало
git worktree remove $SB/main --force
```

Спрашивать надо не «работает ли новое», а «что умел старый код и умеет ли это
новый». Расхождение — либо регресс, либо намеренная правка, и тогда её надо
назвать вслух в теле PR.

## Круг между командами

`create` записала — `rebase` с тем же аргументом обязана это найти; `apply`
положила — `status` обязан увидеть. Нулевой код выхода каждой команды по
отдельности сходимости не доказывает: на этом держалась строка «apply, status и
rebase сходятся», и через неё прошли три дефекта (INS-17).

## Корпус — когда правка задела разбор, применение или откат

Стенд: `/Users/kirillcustom/.claude/jobs/0d36b312/tmp/corpus`

Внутри: `files/` — 300 патчей из публичных репозиториев, `indexed.tsv` — их список, `pp/` — эталонный patch-package 8.0.1, `../oldcode/index.ts` — код проекта до правок, с которым сверяется каждый прогон. Три скрипта:

| скрипт | что проверяет | норма | когда обязателен |
|---|---|---|---|
| `run.ts` | дерево после нашего `apply` против patch-package | **все сравненные совпали**, и с patch-package, и со старым кодом | разбор, применение, построение путей |
| `idempotent.ts` | второй `apply` ничего не меняет | **0 NOT-idempotent** | там же |
| `roundtrip.ts` | `apply` + `rebase 0` возвращает эталон побайтово | **1 not-restored**, известный | откат, инверсия патча |
| `sequences.ts` | патч, разрезанный надвое, даёт то же дерево, что целый; `rebase 1` снимает верхний | **0 DIFFERS и 0 REBASE-DIFFERS**; ожидается 141 `agrees`, 149 `not-splittable`, 1 `single-failed` (@radix-ui) | последовательности, `rebase`, планирование хунков со смещением |

Норма — это «ноль расхождений», а не конкретное число сравненных. С кешем пакетов число почти не гуляет: на прогоне 03.09.2026 сравнено 291 из 292 при одном `no-install`. До кеша оно плавало между 282 и 290, потому что установка ходила в реестр на каждый кейс. Судить всё равно надо по расхождениям, а число сравненных называть вместе с итогом.

Единственный неустранимый `not-restored` — `react-native-launch-navigator+1.0.8`: хунк `@@ -1 +1 @@` в файле из одной строки, исходный перевод строки не сохранился ни в файле, ни в патче. Ещё один патч, `@radix-ui+react-dialog+1.1.6`, стабильно даёт `apply-failed` — и ровно так же он отказывает у patch-package: код выхода 1 у обоих, деревья совпадают. От одного до пяти `no-install` за прогон — это реестр, а не мы.

### Как запускать

Все три скрипта разом, по три шарда: **весь цикл — около трёх минут**, потому что пакеты берутся из кеша (`pkgs/`), а не ставятся заново.

```bash
C=/Users/kirillcustom/.claude/jobs/0d36b312/tmp/corpus
cd $C
for i in 0 1 2; do (bun run.ts $i 3 > shard-$i.log 2>&1 &); done
for i in 0 1 2; do (bun idempotent.ts $i 3 > idem-shard-$i.log 2>&1 &); done
for i in 0 1 2; do (bun roundtrip.ts $i 3 > rt-shard-$i.log 2>&1 &); done
for i in 0 1 2; do (bun sequences.ts $i 3 > seq-shard-$i.log 2>&1 &); done
```

`sequences.ts` идёт дольше прочих — около десяти минут на шард: он готовит по
три дерева на кейс.

Ждать — фоновой командой, а не опросом. Условие по числу живых процессов, а не по слову в логе: упавший шард иначе неотличим от работающего.

```bash
until [ "$(ps -eo command | grep -E 'bun (run|idempotent|roundtrip|sequences)\.ts' | grep -vc grep)" = "0" ]; do sleep 15; done
```

### Кеш пакетов

`pkgs/<пакет>@<версия>/` — распакованные пакеты, общие для трёх скриптов и
переживающие прогоны. Версия в npm неизменяема, поэтому кеш вечен; чистить его
надо только руками, если кончилось место.

Кеша нет или он неполон — налить восемью потоками (~7 минут на все 236 пакетов,
один раз на жизнь стенда):

```bash
cd $C && for i in $(seq 0 7); do (bun warm.ts $i 8 > warm-$i.log 2>&1 &); done
```

Наполняется он **`npm install`, а не `npm pack`**, хотя pack вдвое быстрее.
Проверено: pack даёт другое дерево — npm при установке переименовывает
`.gitignore` в `.npmignore`, а tar оставляет как есть, и каталоги без бита `x`
тоже. На `react-native@0.62.2` это сразу дало расхождение с patch-package и
лишний `not-restored`. Стенд обязан кормить инструменты тем деревом, какое
человек видит после установки (NOT-28).

Раньше установка шла внутри каждого кейса, и один и тот же пакет ставили все
три скрипта: 876 установок на цикл вместо 292, 45–60 минут вместо трёх.

### Как читать итог

`run.ts` печатает сводку в каждый лог:

```bash
for i in 0 1 2; do sed -n '/^сравнено/,$p' shard-$i.log | head -5; done
```

`idempotent.ts` и `roundtrip.ts` пишут JSON — итог собирать из него:

```bash
bun -e '
const fs=require("fs");
const all=[0,1,2].flatMap(i=>JSON.parse(fs.readFileSync(`roundtrip-${i}.json`,"utf-8")));
const by={}; for(const o of all) by[o.status]=(by[o.status]??0)+1;
console.log(all.length, by);
for(const o of all.filter(o=>o.status!=="restored"&&o.status!=="no-install")) console.log(o.status, o.file);
'
```

### Столбец «совпало со старым нашим»

`oldcode` — снимок кода до всех правок, а не движущаяся цель. Расхождение с ним означает «поведение изменилось» — иногда это и есть цель правки. Тогда его надо объяснить, а не молча принять. Расхождение с **patch-package** объяснять сложнее: на нём держится обещание проекта, и менять его можно только осознанно.

### Последовательности: откуда они в корпусе

Реальных последовательностей в собранных патчах почти нет, поэтому `sequences.ts`
делает их сам: режет патч по границе секций, а патч из одной секции — по границе
хунков. Второе и есть случай, которого не знала сюита (INS-14): два хунка одного
файла, где второй ложится уже со смещением от первого.

Два места, где легко получить ложное расхождение, и оба уже проверены:

- **Пустые каталоги.** Откат удаляет файлы, но не убирает каталоги, которые под
  них создавались, — так же ведут себя `git apply -R` и `patch`. Хеш дерева их
  не считает; первая версия скрипта считала и дала 5 ложных расхождений на
  патчах, создающих файлы под `android/build`.
- **Подмена файла патча** (проверка DEC-14) в корпус не пошла: подменить можно
  только половиной того же патча, а половина — подмножество уже применённого,
  то есть она **в дереве**, где отказ не предусмотрен намеренно. Все 141 кейса
  отвечали «не отказал», и это верное поведение. Такой сценарий требует патча,
  которого в дереве нет, и стоит в сюите.

### Чего корпус не ловит

Вложенных зависимостей (`outer++inner`) в нём нет ни одной, секций с симлинками (`mode 120000`) — тоже. Эти случаи закрываются сюитой сквозняком.
