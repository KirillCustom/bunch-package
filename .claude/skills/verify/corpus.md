## Корпус — когда правка задела разбор, применение или откат

Стенд: `/Users/kirillcustom/.claude/jobs/0d36b312/tmp/corpus`

Внутри: `files/` — 376 патчей из публичных репозиториев, `indexed.tsv` — их список, `pp/` — эталонный patch-package 8.0.1, `../oldcode/index.ts` — код проекта до правок, с которым сверяется каждый прогон. Четыре скрипта, и `collect.ts` рядом с ними — им набор добирается:

| скрипт | что проверяет | норма | когда обязателен |
|---|---|---|---|
| `run.ts` | дерево после нашего `apply` против patch-package | **все сравненные совпали**, и с patch-package, и со старым кодом | разбор, применение, построение путей |

Норма — это «ноль расхождений», а не конкретное число сравненных. С кешем пакетов число почти не гуляет: на прогоне 07.09.2026 сравнено **367 из 368** при одном `no-install`, `idempotent` — 366, `roundtrip` — 365 плюс два известных случая. До кеша число плавало между 282 и 290, потому что установка ходила в реестр на каждый кейс. Судить всё равно надо по расхождениям, а число сравненных называть вместе с итогом.

Единственный неустранимый `not-restored` — `react-native-launch-navigator+1.0.8`: хунк `@@ -1 +1 @@` в файле из одной строки, исходный перевод строки не сохранился ни в файле, ни в патче. Ещё один патч, `@radix-ui+react-dialog+1.1.6`, стабильно даёт `apply-failed` — и ровно так же он отказывает у patch-package: код выхода 1 у обоих, деревья совпадают. От одного до пяти `no-install` за прогон — это реестр, а не мы.

### Пятый скрипт: `newer.ts` — перенос на новую версию

Считает, сколько патчей корпуса ложится на следующую версию пакета, и нужен, когда
правка задевает `retarget`. Ходит в реестр за списком версий и ставит по два дерева
на кейс, поэтому идёт дольше прочих; шардируется так же.

Норма (перемерено 07.09.2026 на расширенном наборе): **177 fits, 11 already-there,
97 does-not-fit из 285** (у 80 патчей из 368 новее версии нет, три `no-install`).

Причины этих 97 разобраны, и дешёвого класса среди них нет (NOT-44) — числа держать
рядом, чтобы идея «давайте вытянем остальные» не всплывала заново:

| почему не лёг | кейсов |
|---|---|
| апстрим переписал те самые строки | 77 (79%) |
| файла в новой версии нет вовсе | 11 |
| файла нет, текст или имя нашлись по другому пути | 7, из них настоящий переезд — **3** |
| находится с точностью до пробелов | 2, и это случай DEC-4, а не повод его отменить |

Вложенные зависимости добавили 28 отказов из 97 и распределение не изменили: 23
«переписали строки», 3 «переехал файл», 2 «файла нет».

Раскладку считает `whynot.ts` на стенде: ставит версию, гоняет `apply` и судит **по
дереву**, а не по нашему сообщению об отказе. Трёхстороннее слияние на прежнем
наборе вытягивало 8 из 68 (NOT-19) — потолок известен с двух сторон.

**Вложенное имя пакета в стенде разбирается отдельно.** `packageDir` у такого патча
— это путь `outer/node_modules/inner`, и `npm install`/`npm view` по нему падают.
Ставить надо внутренний пакет, а класть по всему пути. Правило было продублировано
в четырёх местах (`pkgcache.ts`, `newer.ts` дважды, `whynot.ts`) — и все четыре
молча отправляли вложенные кейсы в `no-install` или `no-newer`.

**Патч в корпусе адресуется парой «репозиторий + имя файла».** 68 кейсов носят 57
различных имён: одиннадцать патчей пришли из разных репозиториев под одним именем и
с разным содержимым. Ключ по имени даёт молча не тот файл.

### Как запускать

Все три скрипта разом, по три шарда: **весь цикл — около трёх минут**, потому что пакеты берутся из кеша (`pkgs/`), а не ставятся заново.

```bash
C=/Users/kirillcustom/.claude/jobs/0d36b312/tmp/corpus
cd $C
for i in 0 1 2; do (bun run.ts $i 3 > shard-$i.log 2>&1 &); done
for i in 0 1 2; do (bun idempotent.ts $i 3 > idem-shard-$i.log 2>&1 &); done
for i in 0 1 2; do (bun roundtrip.ts $i 3 > rt-shard-$i.log 2>&1 &); done
for i in 0 1 2; do (bun sequences.ts $i 3 > seq-shard-$i.log 2>&1 &); done
```

`sequences.ts` идёт дольше прочих — около десяти минут на шард: он готовит по
три дерева на кейс.

Ждать — фоновой командой, а не опросом. Условие по числу живых процессов, а не по слову в логе: упавший шард иначе неотличим от работающего.

```bash
until [ "$(ps -eo command | grep -E 'bun (run|idempotent|roundtrip|sequences)\.ts' | grep -vc grep)" = "0" ]; do sleep 15; done
```

### Кеш пакетов

`pkgs/<пакет>@<версия>/` — распакованные пакеты, общие для трёх скриптов и
переживающие прогоны. Версия в npm неизменяема, поэтому кеш вечен; чистить его
надо только руками, если кончилось место.

Кеша нет или он неполон — налить восемью потоками (~7 минут на все 236 пакетов,
один раз на жизнь стенда):

```bash
cd $C && for i in $(seq 0 7); do (bun warm.ts $i 8 > warm-$i.log 2>&1 &); done
```

Наполняется он **`npm install`, а не `npm pack`**, хотя pack вдвое быстрее.
Проверено: pack даёт другое дерево — npm при установке переименовывает
`.gitignore` в `.npmignore`, а tar оставляет как есть, и каталоги без бита `x`
тоже. На `react-native@0.62.2` это сразу дало расхождение с patch-package и
лишний `not-restored`. Стенд обязан кормить инструменты тем деревом, какое
человек видит после установки (NOT-28).

Раньше установка шла внутри каждого кейса, и один и тот же пакет ставили все
три скрипта: 876 установок на цикл вместо 292, 45–60 минут вместо трёх.

### Как читать итог

`run.ts` печатает сводку в каждый лог:

```bash
for i in 0 1 2; do sed -n '/^сравнено/,$p' shard-$i.log | head -5; done
```

`idempotent.ts` и `roundtrip.ts` пишут JSON — итог собирать из него:

```bash

const fs=require("fs");
const all=[0,1,2].flatMap(i=>JSON.parse(fs.readFileSync(`roundtrip-${i}.json`,"utf-8")));
const by={}; for(const o of all) by[o.status]=(by[o.status]??0)+1;
```

### Столбец «совпало со старым нашим»

`oldcode` — снимок кода до всех правок, а не движущаяся цель. Расхождение с ним означает «поведение изменилось» — иногда это и есть цель правки. Тогда его надо объяснить, а не молча принять. Расхождение с **patch-package** объяснять сложнее: на нём держится обещание проекта, и менять его можно только осознанно.

### Последовательности: откуда они в корпусе

Реальных последовательностей в собранных патчах почти нет, поэтому `sequences.ts`
делает их сам: режет патч по границе секций, а патч из одной секции — по границе
хунков. Второе и есть случай, которого не знала сюита (INS-14): два хунка одного
файла, где второй ложится уже со смещением от первого.

Два места, где легко получить ложное расхождение, и оба уже проверены:

- **Пустые каталоги.** Откат удаляет файлы, но не убирает каталоги, которые под
  них создавались, — так же ведут себя `git apply -R` и `patch`. Хеш дерева их
  не считает; первая версия скрипта считала и дала 5 ложных расхождений на
  патчах, создающих файлы под `android/build`.
- **Подмена файла патча** (проверка DEC-14) в корпус не пошла: подменить можно
  только половиной того же патча, а половина — подмножество уже применённого,
  то есть она **в дереве**, где отказ не предусмотрен намеренно. Все 141 кейса
  отвечали «не отказал», и это верное поведение. Такой сценарий требует патча,
  которого в дереве нет, и стоит в сюите.
